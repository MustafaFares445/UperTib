# Wireframe to Component Binding Map

**Phase:** UX 3 - Design System, Session 3 of 7
**Owns:** the `WF-*` to `CMP-*` relation, one row per wireframe, all 165.
**Inventory:** `COMPONENT_INVENTORY.md` and its two block files.
**Patterns:** `INTERACTION_PATTERNS.md`.

## 1. Why this file exists, and what it is not

Phase 3 owns the component taxonomy, so Phase 3 owns the mapping from Phase 2 structure to that
taxonomy. The alternative was annotating the 165 `WF-*` blocks in place, which would edit twelve
files a completed gate approved and make Phase 2 artifacts depend on identifiers that did not exist
when they were approved. **The Phase 2 wireframe files are untouched by this session.**

This file is a **binding**, not a specification. It says which components a wireframe resolves to.
It does not say where they sit, how large they are, what data feeds them, or what they say. Region
placement and widget composition are Phase 4; final copy is Session 4.

Three constraints the file is built to respect:

- Wireframes are referenced **in table cells only, never as headings.** A heading beginning `WF-`
  in this file would enter the Phase 2 wireframe set and demand its own priority order and empty
  and error states.
- The relation is two-way closed. A component defined in the inventory and absent here fails; a
  component named here and absent from the inventory fails. Both directions are real.
- `WF-*` and `SCR-*` are one-to-one on the same domain and numeric suffix, allocated that way by
  Phase 2 to preserve traceability. Both columns are carried anyway, because a reader chasing a
  requirement starts from `SCR-*`.

## 2. How the binding was derived

Not by hand, and not by taste. Each row is computed from facts already in the chain:

| Signal | Source | What it decides |
|---|---|---|
| Platform | `wireframe-manifest.json` | Which profile realizations apply, and that no hover state is emitted on Profile C |
| Archetype | the `WF-*` block fixed priority order | `CMP-PLATFORM-002`, `-006`, `-007`, `-011` and the density mode |
| Lifecycle statuses shown | `INFORMATION_ARCHITECTURE.md` section 11 | `CMP-PLATFORM-001`, bound on exactly the 155 wireframes whose screen records at least one status |
| Roles | the same screen entry | `CMP-PLATFORM-003`, absent on the nine pre-authentication wireframes |
| Domain behaviour | the screen entry purpose, requirements and notes | the seven domain components, plus `CMP-PLATFORM-005`, `-008`, `-012`, `-013`, `-014`, `-015` |

`CMP-PLATFORM-009` and `CMP-PLATFORM-010` are bound on all 165 without exception, because an empty
state and a recovery state are required structural states on every surface.

## 6. What Phase 4 inherits, and what it must not assume

- **This map is a floor, not a ceiling.** A Phase 4 screen spec may place additional framework
  controls and widgets; it may not place a component this map does not bind without adding the row
  here first, because the two-way closure would then break.
- **The Phase 2 wireframe artifacts carry archetype classification, not per-screen region detail.**
  All 165 blocks are generated from five templates and the machine-readable manifest holds
  identifier, screen and platform only. Phase 4 should expect to do its own region work from the
  Phase 1 screen catalog rather than reading it off the wireframes.
- **Density is already decided per row** by archetype and profile, and Phase 4 does not reopen it.
- **A component variant is often decided by the row platform**, not by the screen. The audience
  variants of `CMP-ELIG-003`, `CMP-PLATFORM-002`, `CMP-ELIG-002` and `CMP-CLINICAL-001` follow the
  profile and the actor authorisation, and that boundary is a field-filtering requirement rather
  than a design choice.
